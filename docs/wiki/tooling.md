# Tooling

What formats, lints and typechecks this repository, why each tool is the one here, and what was
measured before believing any of it. Everything on this page was run on 2026-08-27, on the revision
that introduced it.

The short version: **oxfmt formats, oxlint lints the scripts, oxvelte lints the templates,
svelte-check typechecks through TypeScript 7, and bun runs all of it.** Prettier, ESLint and
`lint-staged` are gone.

## Why the toolchain changed

The repositories of this ecosystem - Canari, MiGallery, Sky, le-cercle and this one - are worked on
by the same people, often on the same afternoon. Four formatters with four sets of defaults means a
diff that is mostly whitespace whenever anybody moves between them. So the tools converge; this
page records what that cost here, and it was almost nothing.

## The tools, one by one

### oxfmt - formatting

Configured in [`oxfmt.json`](../../oxfmt.json). The options are the ones the old `.prettierrc`
carried - tabs, 100 columns, **double** quotes, `trailingComma: "es5"` - so the migration is close
to a no-op. **oxfmt disagreed with prettier about two files in the whole repository**:

- `src/lib/server/avatarCache.ts`, a multi-line union type that oxfmt writes with a leading `|`.
  This is the one stylistic disagreement the whole ecosystem hit, in every repository converted.
- `src/app.css`, where prettier had broken `@import url(...) layer(base)` across two lines to stay
  under 100 columns and oxfmt keeps it on one. The at-rule is more readable whole.

Two options are worth naming:

- `endOfLine` is `lf`, because **oxfmt has no `auto`** - the option exists, the value does not, and
  the schema says so. [`.gitattributes`](../../.gitattributes) therefore pins `eol=lf` on checkout.
  Prettier's `auto` preserved whatever was in the file, which is why the repository could go this
  long without the question being forced.
- `ignorePatterns` carries `.prettierignore`'s hard-won entries verbatim, `project.inlang/cache/`
  included: that directory is regenerated by every `paraglide-js compile`, which `prepare` runs on
  every install, so CI produced it before reaching `format:check` and the gate failed on a file
  nobody wrote.

There is **no Tailwind class sorting**. Prettier here never had
`prettier-plugin-tailwindcss` either, so turning `sortTailwindcss` on would rewrite every class
attribute in the repository in the same commit that swaps the toolchain - and reordering utilities
can change which of two conflicting ones wins. It is a decision of its own, not a migration detail.

The formatter is **never run for you**. `lint-staged` is gone with prettier: the pre-commit hook
used to run `prettier --write` and `eslint --fix` over the staged files, which hands you a commit
you have not read. `bun run format` is a thing you type; `bun run format:check` is what the hooks
and the pipeline measure, over the whole tree rather than the staged subset - 87 files in about
half a second, so the staged-only optimisation bought nothing and missed whatever a rebase left
behind.

### oxlint - the script half

Configured in [`.oxlintrc.json`](../../.oxlintrc.json), over the whole repository (`tests/`
included, which the ESLint config had excluded).

The first run reported 13 warnings. All 13 are fixed rather than configured away:

| Warning                                               | Fix                                                                                                                                                                                                                                                           |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 9 `no-unused-vars` in `tests/setup.ts`                | the transition-mock parameters are prefixed `_`, which oxlint's default pattern already honours, and an unused `writable` destructure is deleted                                                                                                              |
| 4 `unicorn/no-new-array` in `src/lib/search/fuzzy.ts` | a file-scoped disable with the reason written out - the four `new Array<T>(n)` calls are dynamic-programming rows the next loop fills completely, and `Array.from({ length: n })` would allocate and iterate on the one path here that runs per candidate row |

The config then disables exactly **one** rule, `no-console`, and it was measured before being
written: turning it back on reports 11 sites, all deliberate server-side logging.

Three more entries were written first and then deleted, each because turning the rule ON reported
**nothing**: `eslint/no-unassigned-vars` (0 - le-cercle needs it for seven `bind:this` declarations,
this repository has none), `typescript/no-explicit-any` (4, all in `tests/setup.ts`, now `unknown`),
and a `typescript/no-unused-vars` policy that duplicated what `eslint/no-unused-vars` was already
doing. A config entry that changes no verdict is worse than none: it tells the next reader that
something is being suppressed.

### oxvelte - the template half

oxlint does not lint Svelte templates - it reads the `<script>` block and stops. `eslint-plugin-svelte`
did, and the tool that replaces it is [oxvelte](https://github.com/tolgaouz/oxvelte), a Rust binary.

**It is pinned to a commit sha**, in [`scripts/install-oxvelte.sh`](../../scripts/install-oxvelte.sh).
It has to be: oxvelte is published on no registry - nothing on npm, no git tag past `v0.1.2` against
a current version of `0.2.0` - so `cargo install --git` with no `--rev` tracks the default branch,
and two machines that ran the same command on different days hold different linters that disagree
about the same file. The installed revision is checked against cargo's own `.crates2.json`, so a
manual `cargo install` is seen exactly like an automatic one.

**It honours the `<!-- eslint-disable-next-line svelte/... -->` comments already in the tree.**
Measured, not assumed: deleting the one in `Seo.svelte` makes a fifth warning appear. That matters
here because the ESLint config carried a whole paragraph about `processor: "svelte/svelte"` being
what made those comments work at all; under oxvelte they simply work.

**Result: zero problems on the recommended set, with no `oxvelte.config.json` at all.** Getting
there took four fixes, described in [backlog](backlog.md) - two `{#each}` blocks keyed, and two
findings justified in place with a comment saying why.

That zero deserves one caveat, and it is the whole of the remaining backlog item: **oxvelte
implements `svelte/no-navigation-without-resolve` more narrowly than eslint-plugin-svelte did.** It
flags a shorthand `{href}` and does not flag a string literal, so the three `href="/associations"`
links in `Footer.svelte` that the older rule reported draw nothing from the new one. Thirteen call
sites the previous gate had an opinion about are now unwatched. They work - `paths: { relative: true }`
and no `base` - but that is a property of the deployment.

### svelte-check and TypeScript 7 - typechecking

`bun run check` runs `svelte-check --tsgo`, which typechecks with the Go compiler
(`@typescript/native`, which is the `typescript@7` package under another name) instead of
`typescript@6`. Both majors are installed and both are needed: svelte-check itself uses the stable
compiler's API, `--tsgo` shells out to the native one. This repository adopted TypeScript 7 before
the toolchain migration; it is refused on Canari, for reasons that are Canari's.

`typescript` is pinned `~6.0.3` rather than `^6.0.3`: the caret would let a minor land unattended
under the compiler svelte-check drives.

## Where each gate runs

| Script                        | pre-commit | pre-push | CI (`Run Tests`) |
| ----------------------------- | ---------- | -------- | ---------------- |
| `format:check` (oxfmt)        | yes        | yes      | yes              |
| `lint` (oxlint)               | yes        | yes      | yes              |
| `lint:svelte` (oxvelte)       | no         | yes      | yes              |
| `check` (svelte-check --tsgo) | no         | yes      | yes              |
| `test` (vitest)               | no         | yes      | yes              |
| `build`                       | no         | yes      | yes              |

`lint:svelte` is out of the pre-commit hook because it builds a Rust binary the first time it runs
on a machine; every run after that is a no-op grep of `.crates2.json`. In CI the binary is restored
from a cache **keyed on the revision** - a key naming `v0.2.0` restores whichever binary was built
first, which is several different linters under one name. Move the key and the pin together.

## Package manager and runtime

bun, everywhere: `bun install`, `bun run`, `bun test` and `bun` as the runtime behind
`svelte-adapter-bun`. The version lives in [`.bun-version`](../../.bun-version) and is repeated in
`packageManager` and `engines`, which is how CI, the deploy runner and a fresh clone resolve the
same toolchain.

**That version is 1.3.8 and the rest of the ecosystem is on 1.4.0**, deliberately, for two reasons
that [deployment](deployment.md) sets out in full: bun's runtime cannot start on the deploy host
from 1.3.9 onward, and 1.4.0 writes `lockfileVersion: 2`, which Dependabot cannot read - a v2
lockfile silently stops every dependency PR here. Both are constraints rather than preferences, so
do not "converge" this number by editing the file.

## What a contributor types

```
bun run format        # rewrite
bun run format:check  # measure
bun run lint          # oxlint, whole repository
bun run lint:svelte   # oxvelte, src only (builds the pinned binary on first use)
bun run check         # svelte-check --tsgo
bun run test
```

`bun run lint:fix` and `bun run lint:svelte:fix` apply what each linter can fix on its own.
